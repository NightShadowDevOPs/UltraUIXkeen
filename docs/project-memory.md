# Project memory — UI Mihomo / Ultra

Этот файл собирает **устойчивый проектный контекст** по репозиторию `NightShadowDevOPs/UltraUIXkeen`, чтобы при переносе в новый чат не приходилось заново восстанавливать договорённости, приоритеты и операционные оговорки.

## Идентичность проекта
- Проект: **UI Mihomo / Ultra**
- Основной репозиторий: `NightShadowDevOPs/UltraUIXkeen`
- Локальная папка: `Y:\Мой диск\Git\UltraUIXkeen`
- Путь на роутере / сервере: `/opt/UltraUIXkeen`
- Стек UI: **Vue 3 + TypeScript**
- Router-agent: shell/cgi-контур на роутере

## Базовые правила релизов
- В каждом релизе нужны:
  - архив релиза;
  - commit message отдельным блоком;
  - команды для роутера отдельным блоком;
  - обновлённые docs, включая файл переноса в новый чат.
- В командах для роутера добавляется `clear`.
- Если меняется `router-agent`, надо отдельно давать команду его обновления на роутере.
- Если меняется `router-agent`, нужно синхронизировать версии в:
  - `router-agent/install.sh`;
  - `api.sh` / status API;
  - документации и handoff-файлах.

## Важный deployment workflow
- Для **UI на роутере** пользователь **не делает `git pull`** как основной путь обновления.
- Обновление UI выполняется **через сам интерфейс UI**.
- Router-agent при необходимости обновляется отдельно через `install.sh`.
- На живом стенде agent проверяется по адресу **`http://192.168.0.1:9099/cgi-bin/api.sh`**. На этом стенде это каноничнее, чем `127.0.0.1`.

## Что уже зафиксировано по архитектуре
- QoS и трафик вынесены в отдельный раздел **«Трафик»**.
- Следующий приоритет после стабилизации HA-контура — доводка раздела «Трафик»: устройства, QoS, бейджи/иконки, устранение дублей.
- При внедрении редактирования `config.yaml` через UI/БД обязательно должен оставаться **эталонный fallback-конфиг**. Если новый конфиг битый, система должна уметь откатиться на рабочий эталон.
- Автоматическую проверку **SSL-сертификатов прокси-провайдеров нельзя ломать**. Любые оптимизации должны сохранять этот функционал, пока пользователь явно не попросит иное.

## Информационная архитектура / UI-ограничения
- Пользователь хочет аудит структуры меню и разделов: текущая IA перегружена.
- Блок управления конфигом Mihomo нужно выносить из `Settings` в отдельный раздел.
- В будущем структура должна становиться чище и более разнесённой по функциональным блокам, без сваливания всего в одну страницу.

## Home Assistant / export-контур
- Текущий рабочий контракт для HA: **`zash.ha.snapshot.v1`**.
- Предпочтительный ресурс для HA: **`ha_snapshot`**.
- Начиная с ветки `v1.2.139+` Home Assistant контур работает через **единый агрегированный snapshot**, чтобы снизить параллельную нагрузку на роутер.
- Внутри `ha_snapshot` уже лежат разделы:
  - `status`
  - `traffic`
  - `users`
  - `qos`
- В релизе `v1.2.141` структура payload **не менялась**.

## Практические выводы по нагрузке
- Для Home Assistant разумно отдавать **операционные снимки**, а не тяжёлую аналитику.
- Сложные весовые диаграммы трафика по клиентам, как в UI-обзоре, лучше не строить через HA polling напрямую.
- Для HA уместны:
  - текущие counters / snapshot-метрики;
  - history / statistics на стороне самого HA;
  - лёгкие time-series без тяжёлой реконструкции flow-графов на роутере.

- не ломать текущий HA-контракт;
- не раздувать опрос HA тяжёлыми диаграммами по клиентам;
- не возвращать git-pull workflow для обновления UI на роутере как основной сценарий;
- не смешивать доработки router-agent и UI без явной необходимости.
